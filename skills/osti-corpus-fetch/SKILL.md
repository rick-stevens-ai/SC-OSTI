# OSTI corpus fetch — discovery, bulk download, consolidation

Rick's OSTI corpus lives at `/Volumes/SG-1-8TB/osti/pdfs/<year>/<osti_id>.pdf` on m1 (canonical, post-2026-06-16 cutover from retired Cherry6TB — see `references/drive-cutover-cherry6tb-to-sg-1-8tb-2026-06-16.md`). Periodic expansion runs query OSTI across DOE labs and years, diff against disk, fetch from CELS DGX, fallback to Unpaywall, hand residual unfetchable list to Ollie for `comments@osti.gov`.

This is the playbook for any "expand / refresh / re-fetch the OSTI corpus" task.

## When to load

- Rick asks to expand or refresh the OSTI corpus.
- Re-fetching empty/corrupt PDFs.
- Building any large-scale OSTI download (>1000 PDFs).
- Generating an "unfetchable papers" report for OSTI support.

For post-fetch corpus analysis (judging, scoring, structured extraction), load `corpus-structured-extraction` instead — this skill stops at "PDFs are on disk."

## Pipeline shape

```
1. RECON (lightweight, lab metadata host OK)
   └─ OSTI API: 10 labs × N years × paginated → recon/<lab>__<year>.jsonl
2. DIFF (m1)
   └─ Union recon osti_ids ⊖ existing PDF basenames in /Volumes/Cherry6TB → fetch_list.jsonl
   └─ Identify 0-byte PDFs in existing corpus → refetch_list.jsonl
3. SMOKE (cels-rbdgx2)
   └─ Fetch 20 new PDFs via PURL → validate (size, content-type, non-empty)
4. BULK FETCH (cels-rbdgx2, parallel 8-16 workers)
   └─ Pull links[].href where rel matches purl/fulltext; fallback construct PURL
   └─ Write to /rbstor/stevens/osti_fulltext_v2/<year>/<id>.pdf
   └─ Log fetch_failures.jsonl on miss
5. UNPAYWALL FALLBACK (cels-rbdgx2 — Unpaywall API works from anywhere)
   └─ For DOI-bearing failures: GET api.unpaywall.org/v2/{doi}?email=...
   └─ Pull best_oa_location.url_for_pdf, fetch + validate
6. UNFETCHABLE LIST (m1)
   └─ Build CSV/JSONL of papers that defeated every fetch path
   └─ kukla-mail send to Ollie with instruction to email comments@osti.gov
7. CONSOLIDATE (m1)
   └─ rsync from cels-rbdgx2:/rbstor/stevens/osti_fulltext_v2/ → /Volumes/Cherry6TB/osti_fulltext/
```

## OSTI API reference

Endpoint: `https://www.osti.gov/api/v1/records`

Key query params:
- `research_org=<lab name string>` — URL-encode the full lab name
- `publication_date_start=MM/DD/YYYY`, `publication_date_end=MM/DD/YYYY`
- `entry_date_start=MM/DD/YYYY` — use for weekly-refresh mode (catches metadata updates to existing records, not just new entries)
- `rows=500` (verified MAX as of 2026-06-13 — `rows=200` and `rows=500` both work; `rows=1000` returns capped at 500). Older docs say `rows=100`; that was conservative, not the actual cap.
- `page=1` (1-indexed)
- Response header `x-total-count` (case-insensitive) gives total for pagination math

Per-record schema you care about:
```
{
  osti_id, doi, title,
  links: [{rel, href}],          // look for rel containing "purl" or "fulltext"
  research_orgs: [...],
  publication_date,
  product_type
}
```

PURL pattern (fallback when no usable link in record):
`https://www.osti.gov/servlets/purl/{osti_id}`

Many records redirect off-site to publishers (escholarship, lab .gov sites) and the response is a redirect chain. Set `--max-time 60`, follow redirects, validate that the final body is `application/pdf` and >10KB.

## Pitfalls

- **Cherry6TB Spotlight wedge** — `ls`/`dd`/eventually `echo` itself all hang. macOS Spotlight reindexing 100K+ files in `_stage_flat/` holds HFS+ catalog lock; wedge cascades to agent shell via `fork()`-blocks-on-cwd-inode. **DO NOT unplug.** Fix from **fresh Terminal.app**: `sudo mdutil -i off /Volumes/Cherry6TB && sudo mdutil -E /Volumes/Cherry6TB`. Keep shell cwd at `~`/`/tmp`. Full recovery: `references/cherry6tb-spotlight-wedge-cascade.md`.
- **Cherry6TB PDF layout is `osti_fulltext/<year>/<year>/<id>.pdf`** — two `<year>` levels nested, not one. A naïve `ls osti_fulltext/2024/*.pdf` returns 1 entry (the inner `2024/` dir) and looks like the corpus is empty. The actual PDFs are at `osti_fulltext/2024/2024/*.pdf`. Sibling `.tar.gz` archives at `osti_fulltext/2024.tar.gz` are snapshots of the inner dir. The `osti_corpus_status.sh` script handles this correctly.
- **contacts.db paper-table year column is `year` (TEXT), NOT `publication_year`.** Schema is `paper(osti_id TEXT PRIMARY KEY, title, year, doi, journal)`. A SELECT against `publication_year` errors with "no such column" — easy mistake from sounding-correct naming. Always read `.schema paper` before composing queries against this DB.
- **0-byte PDFs are silent failures** from earlier redirect-broken fetches. Always validate content-length AND content-type after fetch; never trust HTTP 200 alone.
- **Bare `rbdgx2` ssh hangs** — see hard rule 4. The error mode is a 30-60s hang then connection timeout, not an immediate fail, so it looks like network trouble. Check the hostname first.
- **uicgpu has NO public internet egress** until `source ~/env.sh` runs and exports `HTTP_PROXY=http://<lan-host>:3128`. After that, OSTI API responds in 115ms. NO_PROXY auto-exempts the 100.x.x.x Tailscale range so cross-host operations stay direct.
- **OSTI API can return records with no usable fulltext link** — these are publisher-only abstracts (e.g. ASM journal articles). PURL gets 404. Don't retry these forever; mark and move on.
- **Recon is idempotent by design** — script checks for existing `recon/<lab>__<year>.jsonl` and skips. Safe to interrupt and resume; cells already on disk won't re-query.
- **Don't loop Ollie in on the intermediate work.** Their role on OSTI is only the final `comments@osti.gov` email step. Per Rick (2026-06-07): "Ollie is NOT on the OSTI project."
- **Don't propose elaborate frameworks before smoking the pipeline** — load `corpus-structured-extraction` for the "smoke-test 10-20 records before scaling" rule, then ship one path. Imperative ("expand the corpus") doesn't need a multi-option menu reply.
- **OSTI API rate-limits with HTTP 429 around 12+ parallel-page-fetches.** During a 110-cell recon, 7 cells failed with `HTTP Error 429` on page 1, plus 1 `IncompleteRead` on a long-paginated cell (LBNL 2020, page 412). Don't over-engineer; **just rerun the idempotent script** — cells already on disk get cached, failed cells get retried. Single retry typically lands all but the most stubborn cells. For the stubborn ones, drop concurrency or insert `time.sleep(2)` between pages. Don't add elaborate exponential-backoff machinery until two retries have failed.
- **"Orphans" (papers we have but new recon didn't find) are usually recon coverage gaps, not historical papers from outside the queried window.** When the set-diff comes out surprising (e.g. 1,566 papers in existing corpus but not in fresh recon), DO NOT assume they're pre-window papers. **Probe a stratified sample of ~80 orphan IDs via `https://www.osti.gov/api/v1/records/{id}`** to characterize year + research_orgs + product_type distribution before forming a theory. In the 2026-06-07 run, all 70 probed orphans were 2020 LBNL Journal Articles — the LBNL 2020 cell had the IncompleteRead and the prior corpus had been fetched via a different `research_org` query string. Same year, same lab, same product type — pure coverage gap. The diagnostic takes 2 minutes and prevents an hour of wrong-theory work. See `references/orphan-diagnostic-pattern-2026-06-07.md`.
- **Smoke-fetch yield is roughly 40% direct PDF / 35% HTTP 404 / 20% HTTP 403 / 5% HTML-landing.** Measured on 20 random missing IDs from cels-rbdgx2 against `/servlets/purl/{id}` (2026-06-07). Use this to project bulk-fetch ETAs and Unpaywall fallback queue size: **expect ~40% PURL success → the other ~60% goes to the Unpaywall pass.** Average PURL latency 0.3s on rbdgx2, so ~33K/hr single-threaded, ~5-6 hrs for 110K at 8-way parallel. Re-measure if the OSTI infrastructure changes; the failure-mode mix is the planning input that matters more than the headline success rate.
- **Filter non-paper IDs out of the missing-list BEFORE bulk fetch.** The OSTI API returns records for software/code registrations and datasets alongside papers — these come back with IDs prefixed `code-` (software, e.g. `code-122790`), `dataset-` (datasets), and `biblio-` (some bibliographic records). Their `/servlets/purl/{id}` endpoint serves an HTML landing page, never a PDF, so they always come back as `not_pdf` in the fetch logs and waste a slot per worker. In the 2026-06-07 bulk fetch the recon picked up 1,830 `code-*` IDs out of 110,606 (1.7%) — small fraction, but alphabetical sort front-loaded them so the **first 400 fetches were 100% failure** and looked like the whole job was broken. Diagnostic: `head -10 missing_osti_ids.txt` (if they all share a prefix that isn't numeric, you have non-paper pollution) and breakdown via `awk -F- '{print $1}' missing_osti_ids.txt | sort | uniq -c`. Fix: `grep -v "^code-" missing_osti_ids.txt | grep -v "^dataset-" | grep -v "^biblio-" | shuf > missing_papers_only.txt`. The `shuf` matters too — alphabetical or year-sorted lists pound one bucket at a time; shuffle averages the failure-mode distribution across the run so the early-stop check is meaningful. **Look at the first 200-record fetch-status breakdown before declaring the bulk job healthy** — if `ok` is at 0 while smoke was 40%, kill and re-investigate, don't let it run for hours producing nothing.
- **S2 API key IS provisioned — wire it explicitly in every probe/fetch script.** Rick has a Semantic Scholar API key (40 chars). Canonical locations: m1 login keychain (`semantic-scholar-api-key` / `rick-stevens-ai`, `security find-generic-password -a rick-stevens-ai -s semantic-scholar-api-key -w`), `cherryrd:~/.openclaw/.env` line `S2_API_KEY=...`, `cels-rbdgx2:~/.env` line `S2_API_KEY=...`. With the key, S2 sustains ~7-10 req/s (vs anonymous ~0.25/s after 429 backoff). **Failure mode this session (2026-06-09)**: Phase 3 v2 probe script was throttled to `S2_DELAY=1.2` for anon-tier safety AND `_fetch()` never added the `x-api-key` header — rate collapsed from 3.4/s to 0.6/s under serial 429s. Rule for any S2-touching script: (1) read the key from `~/.env` (rbdgx2/cherryrd) or m1 keychain at script init, (2) print `[init] S2 API key present: {bool}` so misconfiguration is loud, (3) add `headers["x-api-key"] = S2_API_KEY` for any host matching `api.semanticscholar.org`, (4) set delays for the keyed tier (~0.15s per worker, 8 workers fine), (5) if you see rate collapse from N/s → <1/s with `http_429` in error counters, **kill and inspect the key wiring first** — don't wait out an 80-min ETA hoping it recovers. See `references/unpaywall-api.md` for the S2 tier table and the key-loading boilerplate.
- **Hybrid S2+Unpaywall fallback cascade**: see `references/unpaywall-api.md` for the revised cascade. Key revisions from the naive "try S2 after every Unpaywall miss" pattern: (a) only invoke S2 when there is no DOI OR Unpaywall didn't recognize the OSTI-provided DOI, (b) sort `oa_locations[]` by `host_type=repository` first because publisher URLs (Sciencedirect, Wiley, Springer) 403 scrapers even when marked OA, (c) S2 anonymous tier safely sustains ~1 req/4s with a single worker and exponential backoff. Realistic recovery on the failed-bulk pool is 25-40%, not 60-70% — plan the residual unfetchable list (for comments@osti.gov) accordingly.
- **Never hand-build authoritative taxonomies/lists from memory** — always re-derive from the canonical source file. In the 2026-06-07 Genesis classifier work I typed out the 22-topic list from memory and mis-labeled topic 6 as "Nuclear Stockpile / Weapons Modernization (RESERVED)" when the actual NOFO topic 6 is "Transforming Nuclear Restoration and Revitalization" (waste cleanup / EM mission, not weapons). The fix was to rebuild from `~/Dropbox/GENESIS-RFA/GM-NOFO-RFA-AREAS.xlsx` (the structured xlsx — single sheet, columns Topic|Challenge Area|Subtopic|Office|Focus Area). General rule: for any authoritative list (Genesis topics, DOE labs, journal-name canonicalization, etc.), the script's first step is `read the canonical file` — never paste the list as a literal in code or chat. The whole point of canonical sources is they outlast my memory of them.
- **Don't interrupt healthy in-flight runs to absorb a recon-window expansion.** When the recon expands (e.g. backfilling 2006-2015) and produces a fresh, larger candidate pool *while* bulk_fetch / classifier / extractor are mid-stream on the prior pool, the default is to let v1 finish and stage the v2 delta as queued follow-up. Reasons: (a) per-record JSONL outputs are idempotent, so the v2 run just appends without re-doing v1 work, (b) checkpointing bulk_fetch across an input-list swap is non-trivial and breaks ETA semantics, (c) the new IDs aren't going anywhere. Only interrupt if v1 is *broken* (e.g. first-200-record ok-count is 0 from `code-*` pollution). Full staging recipe + empirical scale numbers in `references/year-window-expansion.md`.
- **Before bulk re-fetching from a `failed_recovery.txt`-style pool, run the stage-by-stage failure-class probe first.** Headline recovery rates (e.g. "26% from CELS") look identical for two completely different problems: transient network noise (retryable) vs OSTI access-policy 403 cluster (not retryable, needs an email to `comments@osti.gov`). The probe (`scripts/build_failure_class_sample.py` + `scripts/probe_cels_failure_classes.py`) takes ~12 min on a 40-row stratified-by-lab sample and reveals (a) per-stage failure distribution (metadata vs landing vs PURL vs body), (b) per-lab clustering — failures are usually lab-structural, not random. In the 2026-06-08 probe, PNNL was 100% 403, LBNL/Fermi/JLab were 0% pdf_ok, while Argonne/SLAC/PPPL were 60-100% recoverable — bulk-fetching the whole pool would have wasted >60% of requests. See `references/failure-class-probe-2026-06-08.md` for the full pattern + decision gates.
- **Bulk-decision gates from the failure-class probe**: <30% recovery from CELS → don't bulk, investigate dominant failure class. 30-50% → bulk the recoverable-lab subset only. >50% → whole pool is justified. If `403` cluster dominates, email `comments@osti.gov` before retrying. If `RemoteDisconnected` dominates, throttle to ≤4 workers (probably rate-limited, not access-denied). When deciding whether to retry, classify by stage-3 outcome: `200+not_pdf` and `403`/`404` are NEVER retried (those need escalation), only `RemoteDisconnected` / `timeout` / `5xx` / `tls` / `dnserr` are retry-worthy — full table in `references/failure-class-probe-2026-06-08.md`. Probe output goes to a timestamped run dir on the CELS host (`/rbstor/stevens/osti_probe/probe_cels_<host>_<YYYYMMDD>-<HHMM>/`) with snapshot of probe script + summarize.py alongside results, no PDF bodies retained.
- **Probe BOTH cels-rbdgx2 AND aurora-uan-0009 before any bulk re-fetch — don't assume CELS is fastest.** Discovered 2026-06-09: same 38-ID stratified sample yielded 26% pdf_ok with 11 TCP resets from cels-rbdgx2 vs **63% pdf_ok with 0 resets from aurora-uan-0009**. The per-lab walls (Fermi/JLab returning OSTI's canned 4231-byte "PDF not available" HTML body) are host-independent, but the network reliability and recovery rate change dramatically by fetch path. The right gate is: pull the stratified sample once, run BOTH `scripts/probe_cels_failure_classes.py` (CELS) and `scripts/uan_egress_probe.py` (Aurora UAN), compare per-bucket and per-lab, then bulk from the winner with the unrecoverable-lab subset excluded. As of 2026-06-09 the winner is Aurora UAN by a wide margin. Empirical winner may change over time; always probe both. Full recipe + cross-host table in `references/aurora-uan-egress-2026-06-09.md`.

## Era-specific empirical findings

These are facts about which recovery paths work for which year ranges, learned from running the pipelines against the real corpus. They change planning — don't re-derive them.

- **PURL backfill works well for 2000-2005 (28.9% recovery on 24,945 attempts) but is empty for 2006-2018.** Confirmed 2026-06-14: three independent smokes (2010, 2014, 2017 × 100 IDs each) returned **0/300 recoveries** from `https://www.osti.gov/servlets/purl/{id}` — 290 http_404, 5 redirect_off, 4 wrong_type, 1 exception. The PURL well is exhausted for the 2006-2018 era; OSTI no longer hosts servlet copies of those papers' fulltext. **Recovery for 2006-2018 must go through DOI strategies (Unpaywall → S2 → Crossref → arXiv title+author → freeoa template → EZproxy), NOT bulk PURL fetch.** Of the 111,538 missing PDFs in 2006-2018, 72,143 (64.7%) have DOIs and are eligible for the DOI cascade. Don't waste a multi-hour bulk PURL run trying to fill these — seed `recovery_queue` from `papers` table directly and let `recovery_worker.py` drain it. Per-year missing-with-DOI breakdown 2006-2018: 2006:3073, 2007:3887, 2008:4844, 2009:5408, 2010:5887, 2011:5043, 2012:5886, 2013:5922, 2014:6498, 2015:9306, 2016:5275, 2017:5214, 2018:5900.

- **The 2018-06 SLAC spike (10,700 papers in one month vs ~1,200/month neighbor average) is REAL, not a duplicate-import bug.** Confirmed 2026-06-14: a one-time SLAC Program Document batch deposit via `source=osti_api_bulk_run2`, primary_lab="SLAC National Accelerator Laboratory", product_type="Program Document". Catalog_first_seen 2026-06-13. Don't try to "deduplicate" or "filter" the spike — these are legitimate SLAC operational/program documents. **However, the PDF coverage gap on this batch IS structural**: Program Documents are not PURL-served by OSTI; they appear in the metadata API but their fulltext path is empty. Recovery rate will be near-zero regardless of strategy (DOI cascade won't help — Program Documents don't have publisher DOIs). If you want to drop these from the active corpus, use `scripts/remove_by_product_type.py` with `--types "Program Document"` and they'll log to `decisions` correctly. For now they sit as `papers.has_pdf=0` rows; that's accurate and audit-trail-clean.

- **Promoting `inventory.sqlite.files.{year_from_api,lab_from_api}` → `papers.{year,primary_lab}` is ADDITIVE-ONLY by default — never overwrite existing values on the strength of an API string + regex normalizer.** Confirmed 2026-06-14 on 67,803 OSTI API hits: only 106 papers gained a year (where catalog was NULL), only 215 gained a lab (where catalog was NULL/UNKNOWN). The interesting number is **1,081 lab DIFFERS** — papers where catalog has one primary_lab and the API returns another. The mismatches are NOT noise: top patterns include `ANL → FNAL (86)`, `ORNL → LLNL (80)`, `BNL → FNAL (68)`, `FNAL → SLAC (61)`. Root cause is that OSTI's `research_orgs[0]` (first listed performing organization) doesn't always match the lab that the search-by-research_org query found the paper under — collaboration papers, second-author affiliations, multi-lab grants all produce legitimate divergence. **The right move is**: (1) ship the additive updates (`set year/lab where NULL/UNKNOWN`), (2) park the mismatches as a separate LLM-classifier workstream (Sonnet 4.6 on the full `research_orgs` array + first-author affiliation as the judgment signal), (3) **never use a regex normalizer to overwrite catalog lab** — that's exactly the regex-for-judgment failure mode the hard rule prohibits. Script template at `scripts/promote_year_lab.py` shows the dry-run-with-diagnostic-counts pattern (set/changes/differs separately reported); copy and adapt for any cross-DB additive promotion.
  - **Regex false-positive caught on the same pass: `r'ames|AMES'` matches "NASA Ames" (NASA Ames Research Center).** Use `r'ames laboratory|\bAMES\b'` — require the qualifier or word-boundary acronym. Generalizes to ANY lab abbreviation that's also a common English word (AMES, INL, BNL — single-syllable acronyms are the danger zone). When building a lab-name normalizer for a corpus task, audit the regex against a sample of `OTHER`-bucket strings before treating it as authoritative, and add explicit word-boundary anchors for acronyms.
- **Cherry6TB snap-and-query pattern applies to ALL SQLite DBs on the volume, not just `catalog.sqlite`.** Confirmed 2026-06-14: `_audit/inventory.sqlite` (43MB, 159K rows) hit the same I/O contention wall under concurrent rsync — read-only URI mode timed out at 60s. The `.backup` → `/tmp/inv.sqlite` workaround took 12.9s and yielded full query speed afterwards. Whenever a Cherry6TB-resident DB is needed for inspection during any sustained Cherry I/O (rsync, find, recovery_worker, bulk_fetch — anything hitting the spinning disk), prefer the snap pattern over direct query, even for "small" DBs. The 43MB inventory.sqlite snap is cheap; the 60s timeout is not.
- **Cross-host path-confusion recovery: when a prior-session summary names a path you don't recognize from current state, check BOTH the named path AND the obvious alternative BEFORE acting on the apparent mismatch.** Confirmed 2026-06-14 mid-tar-pipe: prior summary's "active state" block said `/eagle/projects/argonne_tpc/stevens/osti_marker/osti_mirror/` was the mirror root, but a `du -sh` on that path returned `No such file or directory` while the tar receiver was clearly writing somewhere.
